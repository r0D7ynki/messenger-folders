## Cel
`docs/agents/WORKFLOW.md` opisuje tablicę, bramki, role i cykl pracy zgodnie z rojem sb i z `AGENTS.md` po MF-033.

## Kontekst
Sekcje `Tablica` (`docs/agents/WORKFLOW.md:5-18`), `DoR` (`:20-32`), `DoD` (`:34-39`), `Role modeli` (`:41-53`) i `Cykl pracy wykonawcy` (`:55-60`) opisują proces sprzed roju:
- tabela kolumn bez `test`; `done` przesuwa reviewer, a nie rój;
- DoR bez wymogu `batch:`;
- rotacja reviewerów `claude → gemini/human` (w roju: `deepseek` → Claude Opus, `claude` → DeepSeek);
- cykl tylko przez `next --start`/`submit`.

**Stan faktyczny procesu (źródło prawdy dla tej paczki, 2026-10-12):**
1. Kolumny: `backlog → ready → in-progress → test → review → done` (`kanban/config.json` → `columns`). Test jest **przed** przeglądem.
2. Do `ready` karta wchodzi tylko z `batch:` (paczka według modułu, `require_batch`). Podpowiedź: `kanban.py batch plan <model> --apply`. Paczka idzie razem: jeden wykonawca, wspólny test, przegląd na końcu.
3. Karty realizuje **rój sb** (`sb up` / `sb down --agents` / `sb doctor` / `sb upgrade`). Watcher przydziela kartę workerowi (`swarm/worker-N`, worktree w `../.worktrees-messenger-folders/`). Commit workera przechodzi bramkę QA (`npm run verify`) i jest scalany do `swarm/integration`. Potem tester agentowy (`tested_by: auto-test`), reviewer automatyczny (inny model niż wykonawca: `deepseek` → Claude Opus, `claude` → DeepSeek) i auto-done po PASS. FAIL wraca do `ready` z blokerami. Karta z `human_review: true` albo kryterium `(ręcznie)` czeka na człowieka.
4. Gałęzie: workerzy → `swarm/integration` → **jeden** PR do `master` aktualizowany przez `sb pr --push`. Scala opiekun repozytorium. Gałęzie `mf-XXX-…` i `next --start`/`submit` to tryb ręczny (bez roju).
5. Tematy wykryte w trakcie pracy → **nowe karty**. Reviewer i tester oznaczają je `[FOLLOWUP]` (sb zakłada kartę w `backlog`). Wykonawca wpisuje je w sekcji `## Do zgłoszenia` karty albo używa `kanban.py new … --from <ID>`. Pytanie do właściciela trafia do pola `question:` (karta 👤 na tablicy).
6. Planista (`claude`) rozpisuje karty i prowadzi tablicę oraz synchronizację z `origin`. Kart nie realizuje i testów nie uruchamia sam: test i przegląd idą przez sb. Wątpliwość co do karty `done` → `kanban.py move <ID> <kolumna> --reason "…"`, a nie ręczna weryfikacja.
7. Uwagi i błędy dotyczące samego sb → issue w repozytorium swarmboard (`tom3k5/swarmboard`), a nie obejście w tym repo.
8. **Trzy modele w roju, bezpośrednio, bez pośredników** (decyzja właściciela 2026-10-12): `claude` przez Claude Code (worker-1), `deepseek` kluczem bezpośrednio do API DeepSeek (`api.deepseek.com`, `deepseek-flash`, worker-3), `gemini` przez Google Antigravity (worker-2, gdy sb doda workera Antigravity, swarmboard #39; do tego czasu karty `gemini` czekają w `ready`). Reviewer krzyżowy to zawsze inny model niż wykonawca. Limit WIP: 3 w toku, 1 na model, 4 w przeglądzie.
